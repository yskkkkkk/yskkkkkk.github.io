며칠 전 커머스 회사의 광고·성장 관련 팀 면접을 봤습니다. 개발자로 일하면서 처음 겪어보는 라이브 코딩 면접이었습니다.

시작하면서 면접관분께 "사실 라이브 코딩은 오늘이 처음입니다"라고 말씀드렸더니, "아, 정말요?" 하고 조금 놀라시더라고요.

지난 몇 달 동안 면접을 복기하면서 [왜 그렇게 만들었는지](/blog/2026-07-17-questions-from-a-failed-interview/), 그리고 [그 팀에 맞는 사람인지](/blog/2026-10-23-answered-everything-but-not-the-fit/)를 하나씩 고쳐왔습니다.

하나를 메우면 꼭 그다음 빈틈이 보이는 식이었습니다. 이번에는 말로만 답하는 면접에서는 드러나지 않았을 빈틈들을 두 시간 내내 마주하고 왔습니다.

면접은 비대면으로 두 시간 동안 이어졌습니다. 면접관 두 분과 각각 한 시간씩 1회차, 2회차로 나뉘어 진행됐고, 회차마다 화상 회의 링크와 HackerRank(Java 15) 환경이 따로 열렸습니다.

사전 안내 메일에는 답을 완성하는 것 못지않게 전략을 어떻게 세우고 설명하는지, 구현과 디버깅을 어떻게 해나가는지도 중요하다고 적혀 있었습니다. 코드를 쓰기 전에 접근 방식을 말로 먼저 설명하면 좋고, 해결이 어려우면 차선책이라도 설명해 달라는 안내였거든요.

## 2주 동안 준비한 것과 실제 문제

지원한 곳이 광고 관련 팀이라 약 2주 동안은 광고 도메인을 파는 데 시간을 많이 썼습니다.

서빙 경로와 측정 경로의 분리, 클릭 과금 규칙과 부정 클릭 처리, eCPM과 1·2등가 경매, 예산 집행 속도 조절(pacing), 어트리뷰션 윈도우, 노출 유실이나 중복 같은 측정 정합성, 후보 추리기와 빈도 제한, A/B 실험까지 일곱 개 주제로 나눠 공부했습니다.

손을 푸는 코딩 연습도 전부 그 맥락에 맞췄습니다. 중복 과금을 막는 클릭 과금기, 2등가 경매기, 슬라이딩 윈도우 기반 소진 제한기, 어트리뷰션 매칭, 나눗셈 오차를 피하려고 교차곱으로 비교하는 CTR 상위 K 추출까지 열한 문제를 직접 짜보며 익혔거든요.

연습하면서 유독 자주 걸리던 약점들도 따로 추려뒀습니다. `<`와 `<=` 같은 경계값 한 칸 차이, `Map.get`이 돌려준 `null`을 바로 언박싱하다 터지는 NPE, `int` 곱셈 오버플로, `Comparator` 체인 뒤에 `.reversed()`를 붙였을 때 람다 타입 추론이 깨지는 문법 같은 것들이요.

면접 당일 오전에도 손 풀기 삼아 '같은 사용자가 같은 광고를 60초 안에 3번까지만 유효 클릭으로 인정하는 문제'를 하나 풀고 들어갔습니다.

그런데 막상 화면을 열어보니 두 회차 모두 광고 지식을 묻는 문제가 아니었습니다. "광고 팀인데 왜 광고 문제가 하나도 안 나오는 걸까?" 싶더라고요.

알고리즘 퍼즐을 풀거나 빈칸 함수 하나를 채워 넣는 코딩 테스트와도 결이 달랐습니다. 문제 지문은 일부러 넓게 열려 있었고, 지원자가 질문을 던져 범위를 좁히면서 작은 부품을 설계하고 구현해 검증까지 마치는 형식이었습니다.

## 1회차, 최대 N개만 담는 캐시

1회차 문제는 키로 데이터를 조회하는 기능을 구현하는 것이었습니다.

원본 데이터는 DB에 있고, 키를 넘기면 `"DB_" + 키` 형태의 `byte[]`를 반환하는 DB 조회 메서드가 기본으로 주어졌습니다. 이 DB 조회 비용을 줄이려고 앞단에 캐시를 두되, 캐시에는 최대 `N`개까지만 저장해야 한다는 조건이었습니다. `N`개가 다 차면 기존 항목을 비워내야 했고요.

코드를 짜 내려가는 동안 면접관이 제가 쓴 줄들을 보며 하나씩 질문을 던졌습니다.

처음 짚어주신 건 필드에 빠진 `final`이었습니다. 생성자에서 한 번 받고 바뀔 일 없는 용량이나 저장소 참조에 `final`을 빼먹은 거라, 변명 없이 바로 인정하고 고쳤습니다.

다음 질문은 "왜 기본형(`int`) 대신 래퍼 타입을 썼느냐"였습니다. 저는 습관적으로 썼다고 하면서, "`equals`로 비교 방식을 통일할 수 있어 코드 모양이 맞춰지고 최신 자바일수록 그런 쪽이 권고되는 것 같아 따랐다"고 답했거든요.

끝나고 다시 찾아보니 근거가 완전히 반대였습니다. 래퍼 타입에 실수로 `==`를 쓰면 참조 비교가 되고, `Integer`는 `-128`부터 `127`까지만 캐싱하기 때문에 작은 숫자에서는 통과하다가 큰 숫자에서만 틀리는 버그를 만듭니다.

오토박싱 비용과 언박싱 NPE 위험도 있어서, `null` 자체가 '아직 값이 없음'을 뜻해야 하는 자리가 아니면 기본형을 쓰는 게 맞았습니다.

차라리 습관이었다고만 하고 고쳤으면 됐을 텐데, 어설프게 잘못된 근거를 덧붙인 게 훨씬 뼈아팠습니다.

저장소를 `new HashMap<>(N)`으로 초기화한 코드에서도 질문이 이어졌습니다. "왜 `N`으로 초기화했나요? 그게 최대값인가요? `N`개를 넘으면 오류가 나나요?"라는 물음에, 캐시가 최대 `N`개라 처음에 최대값을 줬다고 답했습니다.

이것도 틀린 답이었습니다. `HashMap`이나 `ArrayList` 생성자에 넘기는 숫자는 초기 용량일 뿐 최대 크기를 막아주지 않습니다. 개수가 넘어가면 오류 없이 알아서 배열을 늘립니다.

게다가 `HashMap`은 내부 배열 크기를 2의 거듭제곱으로 잡되 기본 load factor를 `0.75`로 둡니다. 생성자에 `N`을 그대로 넣으면 `N` 값에 따라서는(예를 들어 `N`이 16일 때 임계치가 12가 되어) `N`개를 다 채우기도 전에 리사이즈와 재해시가 일어날 수 있습니다.

리사이즈까지 피하려면 `(int)(N / 0.75f) + 1`을 계산해 넘겼어야 했고, `N`개 상한을 지키는 건 생성자 인자가 아니라 직접 항목을 비워내는 제거(eviction) 로직의 몫이었습니다.

구현 도중에는 캐시 조회와 DB 조회를 한 줄로 줄여보려다 제동이 걸렸습니다. 기억이 정확하지는 않지만 흐름상 이런 형태로 합쳐 썼던 대목이었습니다.

```java
// 면접 당시 한 줄로 합쳐 썼던 흐름 (재구성)
byte[] value = cache.getOrDefault(key, loadFromDb(key));
```

제가 쓰면서도 "이렇게 가져오면 캐시에서 꺼낸 건지 DB에서 새로 읽은 건지 아래에서 구분할 때 한 번 더 확인해야 하네요"라고 중얼거렸더니, 면접관이 "그러면 위에서 값을 이렇게 가져오는 게 잘못된 방식 아닐까요?"라고 되물으셨습니다.

그 자리에서는 히트와 미스 분기를 눈으로 보기 쉽게 나누겠다는 정도로만 답하고 `if` 분기문으로 쪼갰습니다.

돌아와서 직접 실행해 보고 나서야 진짜 문제를 알았습니다. 자바는 메서드를 호출하기 전에 인자 식을 먼저 계산합니다.

`cache.getOrDefault(key, loadFromDb(key))`라고 적는 순간, 캐시에 값이 버젓이 들어 있어도 두 번째 인자를 계산하느라 `loadFromDb(key)`가 매번 실행됩니다. `Optional`에서 `orElse(비싼호출())` 대신 `orElseGet(() -> 비싼호출())`을 써야 하는 이유와 똑같은 원리였는데, DB 호출을 아끼려고 만든 캐시에서 매번 DB를 찌르고 있었던 셈입니다.

용량이 꽉 찼을 때 무엇을 버릴지에 대한 답도 아쉬움이 남았습니다. `Deque`에 키를 담아두고 가장 먼저 들어온 키를 꺼내 지우는 방식으로 고쳤는데, "보통 캐시의 정책에 비춰 FIFO가 맞느냐"는 질문에 "실무에서 이런 조건을 직접 정해본 적이 없다"고 답했거든요.

캐시는 방금 찾은 데이터를 곧 다시 찾을 가능성이 높으니 LRU가 기본이라는 점, 그리고 구현에 들어가기 전에 "오래된 것의 기준이 들어온 순서인가요, 마지막으로 조회한 순서인가요?"를 먼저 물었어야 했다는 걸 복기하면서 정리했습니다.

큐에 왜 키와 값을 묶은 `Entry`를 저장하느냐는 질문에도 "나중에 키를 쓸 수도 있어서"라고 얼버무렸습니다.

생각해보면 이유는 단순했습니다. 용량이 차서 비워낼 때 `Map`에서도 같은 항목을 지워야 하니 키가 필요하고, 실제 데이터(`byte[]`)는 이미 `Map`에 들어 있으니 큐에는 키만 들고 있으면 되는 거였습니다.

긴장한 탓에 마지막까지 "이렇게 하면 되는 게 맞나요?", "맞습니다"를 습관처럼 반복하며 첫 시간을 마쳤습니다.

## 다시 짜본 1회차 코드

면접이 끝난 뒤 Java 15 환경에서 먼저 들어온 걸 비우는 `FifoCache`와, 가장 오래 안 쓴 걸 비우는 `LruCache`를 각각 다시 짜서 돌려봤습니다.

```java
import java.util.*;

// FIFO: 먼저 들어온 키부터 제거
class FifoCache {
    private final int capacity;
    private final Map<String, byte[]> cache = new HashMap<>();
    private final Deque<String> order = new ArrayDeque<>();

    FifoCache(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity: " + capacity);
        this.capacity = capacity;
    }

    byte[] loadFromDb(String key) {
        return ("DB_" + key).getBytes();
    }

    public synchronized byte[] get(String key) {
        byte[] cached = cache.get(key);
        if (cached != null) {
            return cached; // 캐시 히트 시 DB 호출 없음
        }
        byte[] loaded = loadFromDb(key);
        if (cache.size() >= capacity) {
            cache.remove(order.pollFirst());
        }
        cache.put(key, loaded);
        order.addLast(key);
        return loaded;
    }
}

// LRU: 가장 오래 조회하지 않은 키부터 제거
class LruCache {
    private final Map<String, byte[]> cache;

    LruCache(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity: " + capacity);
        this.cache = new LinkedHashMap<>(16, 0.75f, true) { // true = 접근 순서 유지
            @Override
            protected boolean removeEldestEntry(Map.Entry<String, byte[]> eldest) {
                return size() > capacity;
            }
        };
    }

    byte[] loadFromDb(String key) {
        return ("DB_" + key).getBytes();
    }

    public synchronized byte[] get(String key) {
        byte[] cached = cache.get(key);
        if (cached != null) return cached;
        byte[] loaded = loadFromDb(key);
        cache.put(key, loaded);
        return loaded;
    }
}
```

테스트를 돌려보다 보니, `get("a")`가 돌려준 `byte[]` 값(`Arrays.equals`로 비교)만 확인해서는 이게 캐시에서 나온 건지 매번 DB를 다시 읽은 건지 겉으로 드러나지 않더라고요.

그래서 검증할 때는 가짜 DB 메서드가 불린 횟수를 카운터로 같이 셌습니다.

같은 키를 두 번 조회했을 때 DB 호출 수가 그대로 1인지 확인하고, 용량을 2로 둔 뒤 `a, b, a, c` 순서로 조회했을 때 FIFO는 먼저 들어온 `a`를 지우고 LRU는 그사이 한 번 더 쓰인 `a` 대신 `b`를 지우는 것까지 눈으로 확인했습니다.

덧붙여 `byte[]`는 가변 배열이라 그대로 반환하면 호출자가 배열 안의 값을 바꿨을 때 캐시 내부 데이터까지 같이 바뀝니다. 필요에 따라 `clone()`으로 방어적 복사를 할지도 설계 시점에 짚어볼 만한 부분이었습니다.

## 2회차, 외부 API 호출량 제한기

잠시 숨을 돌리고 접속한 2회차에서는 시작할 때 전체 진행 시간을 먼저 안내해 주셨습니다. 처음 5분은 문제를 읽고 질의응답을 하고, 15분 동안 변수와 구현 방식·알고리즘을 말로 함께 설계한 뒤, 45분 동안 구현하고 마지막 10분에 역질문을 하는 구성이었습니다.

설계 뒤에는 코드가 의도대로 돈다는 걸 검증할 수 있는 코드가 꼭 필요하다는 설명도 있었습니다. 꼭 JUnit 형태가 아니어도 괜찮고, 실행이 여의치 않으면 어떤 값을 넣어서 어떻게 확인할지 순서라도 작성해 달라고 하셨습니다.

문제 배경은 대규모 마이크로서비스 환경이었습니다. 서비스 트래픽이 급증하면서 외부 서비스로 과도한 요청을 보내고 있고, 그 여파로 외부 서비스가 간헐적인 응답 지연과 오류를 내면서 내 서비스의 안정성까지 위협받는 상황이었습니다.

외부로 나가는 API 호출량을 제어하는 메커니즘(허용이면 `true`, 한도를 넘으면 `false`를 돌려주는 인터페이스)을 설계하고 구현해야 했고, 요구사항은 크게 두 가지였습니다.

1. 단일 인스턴스에서 **1분에 최대 1,000개**의 요청만 외부 서비스로 전달되도록 보장할 것
2. **시간 단위와 요청량(최대 100만 개)**을 설정할 수 있도록 유연하게 설계할 것

1회차를 겪은 직후라 이번에는 손부터 대지 않고 질의응답으로 문제의 경계부터 좁혔습니다.

- 구현 도중에 요구사항이 추가로 늘어날 수 있나요? → 추가하지 않는다. 대신 지금 문제에서 추상화해 케이스를 뽑아낼 수는 있다.
- 1분에 1,000개가 정확히 보장돼야 하나요, 근사치도 허용되나요? → 명확하게 보장되는 게 중요하다.
- 시간 단위와 요청량을 바꾸는 설정 기능은 처음부터 같이 넣나요? → 1분 1,000개를 먼저 만족시킨 다음에 설정되도록 해도 된다.
- 1분의 기준은 00초부터 01분 00초 전까지를 뜻하나요? → 맞다, 60초라고 생각하면 된다.
- 지문 첫머리에 대규모 MSA라고 되어 있는데 여러 서버 환경을 가정해야 하나요? → 범위를 좁히겠다. 요청은 이 단일 서버로 들어온다.
- 1,000개를 초과한 요청은 버퍼에 담아 다음 1분으로 미루나요? → 아니다. 인터페이스대로 즉시 `false`로 떨어진다.

"정확히 보장해야 하느냐, 근사치냐"를 먼저 물어 확인한 덕분에 알고리즘을 고르기가 한결 수월했습니다.

다만 복기해보니 아쉬운 구석도 있었습니다. "00초부터 01분 전까지"라는 문답이나, 제가 재확인하면서 꺼낸 "피처 플래그 스위치처럼 켜져 있을 때만 `true`인 거냐"는 비유는 자칫 고정 윈도우처럼 읽힐 여지가 있더라고요.

슬라이딩 방식은 1분 내내 스위치가 내려가는 게 아니라 60초가 지난 기록만큼 한 자리씩 다시 열리는 구조니까요. "00분 59초에 1,000개, 01분 00초에 1,000개가 들어오면 막아야 하나요?"라고 숫자를 넣어 물었으면 오해의 여지가 없었을 겁니다.

설계 단계에서 슬라이딩 윈도우를 쓰겠다고 말씀드리니, 면접관이 "이 문제에서 슬라이딩 윈도우가 필요하다고 본 지점이 어디냐"고 물으셨습니다.

시간을 00분~01분, 01분~02분처럼 고정된 칸으로 자르면 앞 구간 끝자락과 뒤 구간 첫머리에 요청이 몰렸을 때 불과 몇 초 사이에 2,000개가 외부로 나갈 수도 있다고 답했습니다. 이 장치의 목적 자체가 외부 서비스 보호이니, 어느 시점에서 직전 60초를 잘라 봐도 1,000개 이하여야 한다는 근거였습니다.

이번 면접을 통틀어 가장 막힘없이 나온 답이었습니다. 알고리즘 이름이 아니라 문제의 목적에서 이유를 꺼냈기 때문이거든요.

다만 설명 말미에 "균등한 요청을 보내야 해서"라는 표현을 섞어 쓴 건 부정확했습니다.

슬라이딩 로그는 어느 60초 구간이든 총량을 1,000개 이하로 묶을 뿐, 첫 1초 안에 1,000개가 한꺼번에 나가는 버스트는 허용합니다. 일정한 속도로 고르게 흘려보내는 건 리키 버킷 쪽 이야기였습니다.

다른 알고리즘과 비교해 달라는 질문에는 고정 윈도우의 단순함과 슬라이딩 윈도우의 계산 부담 정도만 대조하고 넘어갔습니다. 복기하면서 정확도, 메모리 비용, 버스트 허용 특성을 기준으로 다섯 가지 방식을 한눈에 볼 수 있게 다시 정리해뒀습니다.

| 방식 | 정확히 1분 1,000개 보장 | 메모리 | 버스트 특성 |
|---|---|---|---|
| 고정 윈도우 카운터 | 보장 못 함 (경계 전후로 최대 2배 통과) | `O(1)` | 창 경계에 몰리면 2배 허용 |
| 슬라이딩 로그 | 보장함 | `O(한도)` | 1분 한도 안에서는 순간 몰림 허용 |
| 슬라이딩 윈도우 카운터 | 근사치 (`직전 창 × 겹친 비율 + 현재 창`) | `O(1)` | 근사적으로 제한 |
| 토큰 버킷 | 보장 못 함 (60초 구간 최대 약 2배) | `O(1)` | 버킷 크기만큼 순간 몰림 허용 |
| 리키 버킷 | 보장함 | `O(큐 크기)` | 버스트 없음, 일정 속도로 배출 (대기 지연 발생) |

면접관은 조건을 한 발 넓혀서 "만약 인스턴스가 여러 대라면 어떤 저장소를 왜 쓰겠느냐"도 물으셨습니다. 저는 Redis를 쓰겠다고 답하면서 "1,000개가 넘는 이력을 반복해서 조회하는 작업이라 RDB보다 강점이 있다"고 이유를 댔습니다.

선택지는 맞았지만 이유가 정곡을 비껴갔습니다. 여러 서버가 동시에 호출량을 셀 때 가장 먼저 짚어야 할 건 읽기 속도가 아니라 원자성(atomicity)이거든요.

'60초 지난 기록 지우기 → 현재 개수 세기 → 한도 미만이면 새 시각 기록하기'가 한 덩어리로 묶이지 않으면 여러 서버가 동시에 한도 미만이라고 판단해 1,000개를 훌쩍 넘기게 됩니다. Redis는 명령을 단일 스레드로 처리하고 Lua 스크립트로 이 세 단계를 끼어들 틈 없이 묶을 수 있어서 쓰는 거였습니다.

서버마다 시계가 미세하게 다른 문제는 Redis 서버의 `TIME`을 기준으로 삼으면 해결됩니다. `ZSET`에 시각을 점수로 넣어 60초가 지난 기록만 범위로 잘라 지우고, 키 자체에도 TTL을 걸어 요청이 끊긴 키가 남지 않게 정리할 수 있고요.

설정 한도가 100만 개처럼 커지면 `ZSET` 메모리가 부담스러워지니 그때는 정확도를 조금 양보하고 칸 단위 카운터나 토큰 버킷 근사로 타협할 수도 있습니다. 사실 면접 일주일 전에 똑같은 주제를 따로 공부해뒀던 건데, 막상 실전에서는 "읽기가 빨라서"라는 피상적인 말만 튀어나왔습니다.

## 침묵과 검증, 그리고 아침에 풀었던 문제

구현 단계에서는 `Deque<Long>`에 통과한 요청의 시각을 넣어두고, 요청이 올 때마다 `System.currentTimeMillis()`로 현재 시각을 구해 60초가 지난 기록을 앞에서부터 `while`로 꺼내 버리는 코드를 작성했습니다.

도중에 머릿속에 있는 걸 코드로 옮기는 손이 따라주지 않아 "뼈대 코드가 있으면 좋겠다"고 말씀드렸다가, 인터페이스 안에서 직접 구현하며 뽑아내는 편이 좋겠다는 답을 듣기도 했습니다.

코드를 치는 중간에는 "`System.currentTimeMillis()`는 어떻게 생각하고 쓴 건가요?"라는 질문이 나왔습니다. 그때는 그냥 "지금으로부터 60초를 끊으려고 썼다"고만 답하고 넘어갔습니다.

얼추 구현을 마쳤을 때 묵직한 질문이 들어왔습니다.

"이 코드 자체만으로 끝나는 건가요?"

초반 안내에서 분명히 들었던 검증을 제가 먼저 꺼내지 못한 겁니다. 앞서 면접관이 점진적으로 유연성까지 검증할 수 있는 순서를 일부러 말씀드렸다고 짚어주셨는데, 그 의도를 놓치고 있었습니다. 1분에 1,000개 조건을 다 기다려 만들 필요 없이 먼저 1,000번 호출해서 막히는 것부터 확인하고, 시간 관련 로직과 설정 기능은 단계별로 확인하라는 뜻이었거든요.

돌아와서 복기하면서야 구현 도중에 받았던 `System.currentTimeMillis()` 질문의 의도가 하나로 이어졌습니다.

메서드 안쪽에 `System.currentTimeMillis()`를 직접 박아두면, '59.999초에는 막히고 60초 정각에는 다시 열리는지'를 검증하려고 테스트 코드가 진짜로 1분을 멈춰 기다려야 합니다(`Thread.sleep`). 운영체제 시계는 NTP 시간 동기화 과정에서 뒤로 감길 수도 있어서 경과 시간을 잴 때는 `System.nanoTime()`이 더 안전하고요.

처음부터 생성자로 시계(`LongSupplier`)를 주입받게 열어뒀다면 테스트에서 가짜 시계를 넘겨 숫자를 원하는 대로 움직이며 경계값을 그 자리에서 증명할 수 있었을 겁니다. 검증은 구현 뒤에 덧붙이는 마무리가 아니라, 처음부터 시계를 주입받도록 열어두는 설계의 일부더라고요.

검증 코드를 덧붙이고 손보는 과정에서 컴파일 에러도 두 번 만났습니다. 인터페이스를 구현하다 문법 에러가 한 번 났고, HackerRank가 `Solution.java` 파일 하나로 돌아가는 구조인데 같은 파일 안에 만든 구현 클래스에 습관처럼 `public`을 붙였다가 파일명 규칙 에러가 또 났거든요.

당황해서 에러 메시지만 뚫어져라 보며 아무 말 없이 몇십 초를 보냈더니, 면접관이 조용히 말씀하셨습니다.

"저한테 명확하게 질문 주시면 답변을 해드릴 수 있는데, 아무런 얘기 안 하시고 이러시면 제가 답변을 못 해드려요."

정신이 번쩍 들었습니다. 혼자 모니터를 보며 일할 때는 막히면 입을 다물고 생각하는 게 자연스럽지만, 화면 너머의 면접관에게는 그 침묵이 사소한 문법에서 걸린 건지 아예 길을 잃은 건지 알 수 없는 시간이라는 걸 그때 처음 실감했습니다.

면접이 모두 끝나고 복기하다가 허탈하게 웃음이 나온 대목도 있었습니다. 당일 아침 워밍업으로 풀었던 '60초 안에 유효 클릭 3번까지만 인정하는 문제'가 이 호출량 제한기와 똑같은 문제였더라고요.

`Deque<Long>`에 래퍼 객체를 쌓고 매번 `while`로 비워내는 대신, 크기 `limit`짜리 기본형 `long[]` 원형 배열을 두면 훨씬 간결해집니다. 배열이 다 찼을 때 가장 오래된 시각 딱 한 칸(`times[head]`)만 확인하면 끝나거든요.

그 한 칸이 60초 밖으로 밀려났다면 그 자리에 새 시각을 덮어쓰고 `head`만 한 칸 옮겨 통과시키면 되고, 아직 60초 안이라면 창 안에 `limit`개가 꽉 차 있다는 뜻이니 바로 `false`를 돌려주면 됩니다.

요청당 연산은 정확히 `O(1)`이 되고, 문제의 최대 조건인 100만 개로 설정해도 박싱 오버헤드 없이 `long` 백만 개(`8MB`)로 메모리가 고정됩니다. 이 구조로 다시 작성해 검증까지 마친 코드는 아래와 같습니다.

```java
import java.util.concurrent.TimeUnit;
import java.util.function.LongSupplier;

interface RateLimiter {
    boolean request();
}

class SlidingWindowRateLimiter implements RateLimiter {
    private static final int MAX_LIMIT = 1_000_000;

    private final int limit;
    private final long windowNanos;
    private final LongSupplier clock; // 검증 시 시간을 직접 제어하기 위해 주입
    private final long[] times;       // 최근 허용한 시각을 담는 원형 배열
    private int head = 0;             // 가장 오래된 시각의 인덱스
    private int size = 0;             // 현재 채워진 개수 (최대 limit)

    SlidingWindowRateLimiter(int limit, long window, TimeUnit unit) {
        this(limit, window, unit, System::nanoTime);
    }

    SlidingWindowRateLimiter(int limit, long window, TimeUnit unit, LongSupplier clock) {
        if (limit <= 0 || limit > MAX_LIMIT) {
            throw new IllegalArgumentException("limit must be 1.." + MAX_LIMIT + ": " + limit);
        }
        if (window <= 0) {
            throw new IllegalArgumentException("window must be positive: " + window);
        }
        this.limit = limit;
        this.windowNanos = unit.toNanos(window);
        this.clock = clock;
        this.times = new long[limit];
    }

    @Override
    public synchronized boolean request() {
        long now = clock.getAsLong();
        if (size < limit) {
            times[(head + size) % limit] = now;
            size++;
            return true;
        }
        if (now - times[head] >= windowNanos) { // 가장 오래된 허용 시각이 창 밖으로 나감
            times[head] = now;
            head = (head + 1) % limit;
            return true;
        }
        return false;
    }
}
```

시계를 밖에서 주입받게 바꾸고 나니 면접관이 힌트로 주셨던 검증 순서도 그대로 코드로 옮길 수 있었습니다.

1. 같은 시각에 1,001번 요청했을 때 1,000번은 `true`, 1,001번째는 `false`가 나오는지 확인
2. 0초에 1,000개를 채운 뒤 시계를 `59,999ms`로 옮기면 `false`, 정확히 `60,000ms`로 옮기면 다시 1,000개가 통과하는지 확인
3. 59초에 1,000개를 통과시킨 뒤 60초에 추가 요청을 보냈을 때 전부 거절되는지 확인 (고정 윈도우였다면 뚫렸을 경계 케이스)
4. 0초에 500개, 30초에 500개를 보낸 뒤 60초에는 딱 500자리만 열리고 90초에 나머지 500자리가 열리는지 확인
5. 설정을 `1초당 3개`로 바꿨을 때와, 스레드 10개가 동시에 200번씩 총 2,000번을 호출했을 때 정확히 1,000개만 통과하는지 확인

마지막 역질문 시간에는 솔직한 궁금증을 여쭤봤습니다. 광고 팀이라 광고 도메인 문제를 예상하고 준비했는데 두 회차 모두 백엔드 전반에 해당하는 문제가 나왔다고, 오늘 다룬 문제들이 실제 광고 시스템에서는 어떤 지점과 맞닿아 있는지 물었거든요.

면접이 끝난 뒤 혼자 이어 붙여보니, 최대 `N`개 캐시는 수십 ms 안에 응답을 끝내야 하는 광고 후보·소재 로컬 캐시와 닿아 있었습니다. 슬라이딩 윈도우 제한기도 같은 사용자에게 같은 광고를 한 시간에 몇 번까지만 보여줄지 정하는 노출 빈도 제한(frequency cap)이나, 짧은 시간의 반복 클릭을 걸러내는 부정 클릭 방지 로직과 구조가 같았고요.

## 돌아보며 정리한 여섯 가지 차이

두 시간을 돌아보니 면접관이 본 건 자바 기본기를 정확한 이유와 함께 쓰는가, 고른 방식의 근거와 포기한 대가를 말할 수 있는가, 내 코드가 맞다는 걸 스스로 증명할 수 있게 짜는가였던 것 같습니다.

2회차 초반에 질문으로 조건을 잘 좁혀놓고도, 그 합의된 내용을 에디터 상단에 주석으로 적어두지 않고 머릿속에만 둔 채 바로 코드를 치기 시작한 점도 아쉬웠습니다. 에디터 맨 위에 아래 여덟 줄만 먼저 적어뒀어도 구현하다 길을 잃거나 검증을 빠뜨리지 않았을 겁니다.

```java
// [확정한 조건]
// - 어느 60초 구간에서도 허용 요청은 정확히 1,000개 이하
// - 초과 요청은 대기 없이 즉시 false 반환
```

말끝마다 "이렇게 하면 되는 게 맞나요?"라며 정답 확인을 구했던 태도도 계속 걸렸습니다. 문제를 출제한 사람에게 허락을 구하기보다, 선택지들을 나란히 꺼내놓고 트레이드오프를 짚은 뒤 내 결정을 제안하는 모습이 그 연차에 기대하는 태도였을 테니까요.

복기 노트를 정리하면서, 면접장에서 아쉬웠던 제 반응과 바꿨어야 할 판단을 여섯 가지 기준으로 대조해 적어봤습니다.

| 기준 | 면접장에서 아쉬웠던 내 반응 | 바꿨어야 할 판단과 표현 |
|---|---|---|
| 도구의 특징보다 문제의 목적을 먼저 본다 | 다중 서버 저장소 질문에 "반복 읽기가 빨라서 Redis를 쓴다"고 답함 | "여러 서버가 동시에 셀 때도 한도를 절대 넘기지 않는 게 목적이니 원자성이 핵심입니다. 단일 스레드와 Lua 스크립트로 묶을 수 있는 Redis를 쓰겠습니다." |
| 선택지를 내놓고, 결정하고, 포기한 것을 말한다 | "가장 오래된 걸 지우면 되는 게 맞나요?" | "FIFO와 LRU가 있는데, 캐시는 최근 쓴 걸 다시 쓸 가능성이 커서 LRU로 가겠습니다. 대신 조회마다 순서를 갱신하는 비용은 감수하겠습니다." |
| 범위를 스스로 끊어 정한다 | 면접관이 검증과 구현 순서를 힌트로 알려줌 | "단일 서버에서 1분 1,000개를 먼저 만들고 검증한 뒤에 설정 기능을 붙이고, 다중 서버 환경은 설계만 말씀드리겠습니다." |
| 시키지 않아도 기본이 손에 배어 있다 | 면접관이 `final` 누락과 래퍼 타입 사용을 짚어줌 | 처음 코드를 칠 때부터 불변 필드에 `final`, 불필요한 박싱 배제, 입력값 범위 검증, 시계 의존성 분리 |
| 어디서 깨질지 먼저 꺼낸다 | 동시성이나 시계 이야기를 질문받고 나서야 생각함 | "여러 스레드가 동시에 부를 때의 원자성, 시계 보정 문제, 한도를 100만으로 키웠을 때의 메모리부터 짚어보겠습니다." |
| 검증을 설계의 일부로 다룬다 | 구현 후 "이 코드 자체만으로 끝나는 건가요?"라는 질문을 받음 | 코드를 치기 전에 "이 세 가지 케이스로 확인하겠습니다"를 먼저 적고, 테스트에서 시간을 움직일 수 있게 시계를 주입받도록 설계 |

경험해 보지 못한 영역을 질문받았을 때도 이 틀은 그대로 쓸 수 있더라고요.

"실무에서 용량 제한 정책을 직접 정해본 적은 없다"에서 말을 끝내면 대화가 멈추지만, "직접 정해본 적은 없지만 캐시는 최근 조회한 데이터를 다시 찾을 가능성이 크니 원리상 LRU가 맞을 것 같다"고 이어가면 모르는 상태에서도 어떻게 판단을 내리는지는 보여줄 수 있으니까요.

이번 면접을 겪고 나서 연습 방식도 완전히 바꿨습니다. 알고리즘 사이트에서 입출력이 정해진 함수 빈칸을 채우는 대신, "외부 결제 API 장애에 내 서비스가 같이 무너진다, 막는 장치를 만들어라"처럼 일부러 넓은 문제를 두고 시작합니다.

질문으로 범위를 좁혀 확정 조건과 검증 케이스를 주석으로 먼저 적고, 선택지가 갈리는 지점마다 이유와 한계를 소리 내어 말하며 구현하는 연습입니다.
