4년 동안 백엔드를 짰다. Spring Boot, JPA, 트랜잭션, 인증 — 이 영역은 자신 있다. 근데 개인 포트폴리오를 만들려다 보니 이상한 문제가 생겼다. 내가 만든 것들에 백엔드가 없었다.

회사 코드는 공개할 수 없다. 개인 프로젝트가 내 실력을 보여주는 유일한 창구인데, 거기에 내가 4년 동안 쌓아온 것들이 하나도 안 들어가 있으면 의미가 없다.

## Pet-Pass가 가르쳐준 것

피카밈 전에 Pet-Pass라는 반려동물 관련 지도 앱을 만들었다. AI와 협업해서 3주 만에 완성했다. 잘 돌아간다. 아무도 안 쓴다.

왜 실패했는지는 금방 보였다. 이미 비슷한 앱이 여럿 있었고, Pet-Pass가 그것들보다 뭔가 명확히 나은 게 없었다. 기능이 없어서가 아니라, 굳이 올 이유가 없었던 거다. 지도 앱이라 진입에도 맥락이 필요했고, 결과를 저장하거나 공유할 구조도 없었다.

> [!NOTE]
> 기능이 있다고 사람이 오는 게 아니다. 굳이 와야 할 이유가 있어야 한다.

실패 원인이 명확하니까 역으로 다음 조건이 나왔다.

1. **⚡ 즉각성**: 들어와서 5초 안에 결과가 나와야 한다
2. **📤 바이럴**: 결과를 자랑하고 싶게 만들어야 한다
3. **🧩 단순함**: 처음 온 사람도 바로 쓸 수 있어야 한다

조건을 쓰고 나니 아이디어가 빠르게 좁혀졌다. B급 감성 동물 사진에 '킹받는' 문구를 붙이는 가챠형 밈 생성기. 버튼 하나면 끝나고, 결과를 저장하거나 공유하고 싶어진다. 이게 피카밈의 시작이었다.

## 먼저 프론트만 짰다

아이디어가 실제로 되는지 빠르게 검증하고 싶었다. Next.js로 프론트엔드만 짰다. 백엔드 없이, 이미지 파일과 문구 배열을 정적으로 조합하는 방식이었다.

동작은 했다. 동물 이미지 + 문구가 랜덤 조합되고, 결과물이 나왔다. 개념 자체는 증명됐다.

근데 뭔가 허전했다. 하트 시스템도 없고, 로그인도 없고, 저장도 안 된다. 사용자가 무언가를 하면 서버가 반응해야 하는 부분들이 전부 빠져 있었다. 그리고 무엇보다 — 백엔드 개발자가 만든 프로젝트인데 백엔드가 없었다. 포트폴리오로 낼 수 있는 수준이 아니었다.

## BaaS냐, 직접 짜기냐

백엔드를 붙이기로 했다. 선택지는 두 가지였다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **Supabase (BaaS)** | PostgreSQL + Auth + Storage를 한 번에 해결. 빠르게 만들 수 있다. | JPA 없음. Spring Security 없음. 내가 쌓아온 것들이 보이지 않는다. |
| **Kotlin + Spring Boot (선택)** | JPA, 트랜잭션, Security, 아키텍처 설계 — 백엔드 역량을 직접 보여줄 수 있다. | 초기 세팅에 시간이 훨씬 더 든다. |

Supabase가 편한 건 맞다. 근데 포트폴리오 목적이 명확한 프로젝트에서 BaaS를 쓰면 내가 증명하고 싶은 게 사라진다. JPA를 쓸 일도 없고, Spring Security를 설계할 일도 없다. 4년 동안 쌓아온 것들이 아무것도 안 들어가는 프로젝트가 된다.

그래서 Kotlin + Spring Boot로 직접 짜기로 했다. Java 대신 Kotlin을 선택한 이유는 단순했다. JVM 생태계는 그대로 쓰면서 null safety, data class, 확장 함수 같은 표현력이 올라간다. Spring Boot와 궁합도 좋다.

## 스택을 결정했다

DB는 PostgreSQL이 자연스러운 선택이었다. MySQL도 고민했지만 JSON 처리, 확장성, 그리고 생태계 측면에서 PostgreSQL을 선택했다. 호스팅은 NEON — 서버리스 PostgreSQL로 무료 티어 내에서 충분히 돌아간다.

| 역할 | 선택 | 선택 이유 |
|---|---|---|
| 백엔드 | **Kotlin + Spring Boot** | JPA, Spring Security, Clean Architecture. 백엔드 역량 증명. |
| 데이터베이스 | **NEON (PostgreSQL)** | 서버리스 PostgreSQL. 무료 티어. MySQL 대비 JSON 처리 우위. |
| 캐시 / 하트 | **Upstash Redis** | 서버리스 Redis. 무료 티어. 하트 충전 Lazy Charging에 적합. |
| 이미지 저장 | **Cloudflare R2** | S3 호환 API. 이그레스 비용 없음. |
| 프론트엔드 | **Next.js 14 (App Router)** | 기존 프로토타입 기반. SSR + RSC 활용. |

Gradle 멀티 모듈로 백엔드를 4개 계층으로 분리했다. Clean Architecture + DDD로 설계한 이유는 Pet-Pass에서 배운 것 때문이었다 — 구조 없이 기능을 쌓으면 나중에 무너진다. 이 부분은 다음 글에서 이어진다.

## 서비스 요건 세 가지

스택이 정해졌으면 서비스 구조를 확정해야 했다. Pet-Pass 실패 원인의 반대로 설계했다.

버튼 하나면 이미지, 문구, 스티커가 무작위로 조합된다. 결과가 마음에 안 들면 하트를 써서 다시 뽑는다. 하트는 시간이 지나면 차오른다 — 모바일 게임의 스태미너와 같은 구조다.

로그인 사용자에게는 워터마크 없는 결과물을, 비로그인 사용자에게는 워터마크가 있는 결과물을 준다. 이 차이가 자연스러운 로그인 유도 수단이 된다. 공유하고 싶은데 워터마크가 거슬리면 로그인하게 된다.

> [!TIP]
> 가챠에서 중요한 건 결과물이 아니라 뽑는 순간이다. 기대감이 있어야 다시 누른다.
